# **Project Reflection**

## What worked well 
Acquiring necessary data for this project was surprisingly seamless. This was mainly due to the FRA's Blocked Crossing historical dataset which is available to the public and simple to filter by date, city, state, even rail company. The FRA webpage has several graphs and infographics to easily make sense of the data visually. The ease of exporting an .xlsx file with filtered settings, made the task of data preprocessing and cleaning easier.

Additionally, the data preprocessing and cleaning stage also worked well. The dataset naturally has missing fields as it is collected from public reports of rail blockages where public reporters might omit certain fields. This was handled by simply removing irrelevant columns (like `Time_Window` and `Additional Comments`), removing duplicate reports, and filling in missing fields with standardized data ie. missing fields in `County` are filled in with `Harris`. Reducing the dataset to focus on Union Pacific reports only (98.3% of the original dataset) further simplified the overall process. The final cleaned dataset contained 16,864 records after starting with 20,783 records.

Training the GRU classifier exceeded my expectations: the model performed at an 85% accuracy on data that was sourced from a dataset of generated public reports. Lowering the threshold from 0.50 to 0.40 improved recall from 84.9% to 89.7%, which shows that the agent now catches nearly 90% of high risk events, an important milestone given the intended purpose of this agent. The demos showed that the agent had actually learned real patterns, when Leeland Street at rush hour returned a 93% HIGH vs 6% overnight LOW risk, reflecting real trends. I was really happy with the outcome despite time limitations and having to scale back from the original midterm plan.

Lastly, the addition of a street name lookup tool made the agent much more user friendly and practical. At first the agent's output was only displaying the Crossing IDs, a series of numbers and letters, for example "411912V". After adding the tool, the name of the street populated in the output instead, which in a real world scenario, like with an emergency dispatcher, would save time in looking up or memorizing Crossing IDs.

## What did not work and how it was handled
One major thing that did not work was the GRU blockage duration prediction model. The R-squared metric showed that it could only explain 4.6% of the variation in blockage duration, indicating that it had not learned anything meaningful and was performing about the same as random guessing. It became apparent that the FRA dataset was not suited for this type of model as blockage duration happens due to circumstances not reflected in the data, like train yard congestion, Union Pacific operational decisions, and even mechanical issues. After that, I made the decision to pivot to a GRU binary classification model that would focus solely on the probability a crossing was blocked. 

Another thing that didn't work was the TranStar API which returned a 403 error, meaning access denied. This was disappointing and after doing some research it could be due to various reasons like IP address restrictions (it is a government data feed) or the TranStar API requiring an access token registration. I ended up documenting the failed attempt and moving on.

One other initially concerning hurdle was upon testing the agent and observing it use multiple tools successfully, it returned a final answer of "N/A". This was due to relying on the default ReAct prompt from LangChain which was not strictly enforcing a complete final answer. This was fixed by adding a custom Houston dispatch prompt that added explicit instructions for the agent, telling it that it must always respond with a complete response and never respond with "N/A". The clearer instruction prompt seemed to solve this issue. 

## Biggest technical challenge and how it was solved
The biggest technical challenge that I faced was trying to get LangChain to work in Google Colab as every time I tried to use the OpenAI API I got an error message. At first I thought it was a problem with the versions of the packages (specifically a version conflict between OpenAI and LangChain), but after trying many times to fix it I realized I had to try something different. So after many tries with the help of a coding assistant, I added a patch to the notebook to remove the proxy settings that Colab was adding. This patch fixed the problem by removing the settings before they could cause the OpenAI client to crash, ultimately solving the problem altogether. This challenge was really frustrating because fixing the version conflict did not work. It was a lesson in reading the error messages carefully and dealing with the challenges of choosing not to work on the project locally.

## Path changes from the Midterm blueprint
In the midterm I chose Option A - the Single Agent and it remained the same for this Final project. Most of the changes that were made came in the form of scaling back due to time constraints. After reading Professor McManus' feedback on the Midterm, I decided to put the RL rerouting portion of the project on the back burner. I also radically changed the appearance of my architecture diagram to rely less on prose and more on letting images explain the makeup and flow of the agent. In the Midterm I had not landed on a specific model architecture yet, I was oscillating between RNN and Transformer, but ended up choosing the GRU model (RNN) because of its faster training time. I scaled back the data inputs to just one historical dataset and no live data. My reasoning for this was that a.) the FRA blockage dataset was robust enough to implement the model and b.) TranStar and TrainWatch APIs denied access to what would have been their live data feeds. As I explained earlier, the duration prediction model was replaced due to poor performance with a binary classification model. Additions to the original blueprint include creating the street name lookup tool and adding a custom ReAct prompt. 

## What I would build next
My original plan was, in retrospect, a huge undertaking that I admittedly did not have the time for. I will chalk it up to overenthusiasm. If I had more time, I would try to incorporate more datasets than the one I ended up using. I would also perform more fine-tuning and optimization on the GRU model. Long term, working on an RL-based rerouting tool would also greatly improve the usefulness of this agent as well as implementing a front-end user interface. Lastly, gaining access to certain government-run APIs like TrainWatch and TranStar would be a game changer in terms of what this agent could be capable of.
